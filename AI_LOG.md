# Как использовался ИИ

## Инструменты и организация

Работал в Codex с моделью семейства GPT-6. Ведущий агент по очереди подключал
агентов в ролях бэкенд-разработчика, тестировщика и DevOps; одновременно работали
не более двух агентов. Другие ИИ-инструменты не использовались. ТЗ читали через
`pypdf`, результат проверяли pytest, httpx, Ruff, Alembic и Docker Compose.

## Ключевые запросы

1. Бэкенду: «Реализуй API по ТЗ: деньги только в целых копейках, точный график
   рассрочки, идемпотентность с уникальным ключом, разрешённые переходы статусов
   и HMAC по сырым байтам вебхука». После уточнения: «Раздели HTTP, бизнес-логику
   и SQLAlchemy; PostgreSQL сделай штатной БД».
2. Тестировщику: «Проверь pytest + httpx суммы и промокод в разном регистре,
   график на 3/6/12 месяцев, отсутствие дубля, переходы и 409 без изменения
   статуса, 404, подпись вебхука и фильтры. Проверяй содержимое ответов».
3. DevOps: «Подготовь Docker Compose с PostgreSQL, миграцией перед стартом API,
   GitHub Actions с Ruff и pytest, README с командами и curl-примерами, правила
   для ассистента в репозитории».

## Что сделал каждый агент

**Бэкенд-разработчик.** Реализовал модели тарифа и платежа, валидацию запросов,
расчёт скидки и графика без `float`, идемпотентное создание платежа и переходы
статусов. Уникальный ключ в БД и обработка `IntegrityError` закрывают гонку
между двумя запросами. Условное обновление статуса проверяет, что он не успел
измениться до записи. После уточнения владельца разделил код на HTTP, сервисы
и репозитории, переключил штатный URL БД на PostgreSQL.

**Тестировщик.** Создал `tests/test_api.py` с 20 проверками обязательных
сценариев и бонусов. Тесты используют отдельную SQLite-базу для каждого случая
и проверяют не только HTTP-код, но и суммы, график, тело ответа и отсутствие
второго платежа через `GET /payments`. В этом Windows-окружении `TestClient`
зависал даже на пустом FastAPI-приложении, поэтому тесты используют
`httpx.ASGITransport`; проблему среды не стали маскировать изменением API.

**DevOps.** Подготовил `Dockerfile`, `compose.yaml` с PostgreSQL и проверкой
готовности, `.env.example`, CI на push и pull request, README и `AGENTS.md`.
Контейнер API ждёт готовности БД, применяет Alembic и затем запускает Uvicorn.
DevOps проверил сборку и реальные запросы: тарифы — 200, создание платежа — 201,
подписанный вебхук — 200; `alembic check` на PostgreSQL не нашёл расхождений.

**Ведущий агент.** Разобрал ТЗ, распределил задачи, настроил зависимости и
создал начальную миграцию Alembic. На ревью обнаружил два слабых решения:
`create_all()` при старте создал бы таблицы без записи версии Alembic, а разбор
JSON до HMAC мог вернуть 422 вместо 401 для запроса с неверной подписью.
Бэкенд-агент исправил оба случая. По последующему запросу владельца ведущий
агент разнёс `api/`, `schemas/`, `services/`, `repositories/` и `models/` по
папкам с отдельными модулями тарифа и платежа, обновил импорты, тесты и README.

## Итоговая проверка и границы

После последнего переноса: 20 тестов прошли, `ruff check .` чист, Alembic
применяет миграцию и не видит изменений схемы. Образ заново собран; API и
PostgreSQL стали healthy, `GET /tariffs` вернул 200. Тесты API выполняются на
SQLite; PostgreSQL проверен отдельно миграцией и запросами через Compose.
GitHub Actions подготовлен, но удалённый workflow не запускался: по решению
владельца проект оставлен локальным.
